Module 1: Advanced Analytical SQL on Cloud Big Data (Weeks 1 - 4)

1.1 The True 10-Step Query Execution Order

While developers compose SQL starting with SELECT, the MySQL 8.0 query optimizer and execution engine process statements in an entirely different pipeline: 

Step 1: FROM                 -> Identifies base tables
Step 2: ON                   -> Evaluates join conditions per row pair
Step 3: JOIN                 -> Generates combined virtual joined table
Step 4: WHERE                -> Filters individual rows before aggregation
Step 5: GROUP BY             -> Buckets filtered rows into distinct groups
Step 6: WITH ROLLUP / CUBE   -> Injects dimensional super-aggregates
Step 7: HAVING               -> Filters aggregated groups
Step 8: SELECT               -> Evaluates projections, window functions & aliases
Step 9: DISTINCT             -> Deduplicates identical output tuples
Step 10: ORDER BY            -> Sorts the result stream (can access SELECT aliases)
Step 11: LIMIT / OFFSET      -> Paginates and truncates the stream
💡 The Senior Interview Trap: Why does WHERE total_price > 100 fail when (unit_price * qty) AS total_price is aliased in SELECT?
Engine Architecture: WHERE (Step 4) is evaluated before SELECT (Step 8). At Step 4, the alias does not exist yet in the database engine's working memory. To fix: repeat the expression in WHERE or encapsulate the calculation in a Common Table Expression (CTE).

1.2 Self-Joins & Market Basket Co-Occurrence

On large datasets like Stack Overflow (50M+ posts) or e-commerce transactions, identifying items that frequently appear together requires joining a table to itself using a strict inequality constraint: 

SELECT 
    p1.tags AS tag_a,
    p2.tags AS tag_b,
    COUNT(*) AS shared_questions
FROM so_posts p1
JOIN so_posts p2 
    ON p1.post_id = p2.post_id 
   AND p1.tags < p2.tags -- CRITICAL: Prevents duplicate pairs (A,B)/(B,A) and self-pairs (A,A)
GROUP BY p1.tags, p2.tags
HAVING shared_questions >= 5
ORDER BY shared_questions DESC;

2.2 The High-Cardinality Hash Indexing Trap (Git SHA & Bitcoin Hashes)

⚠️ Why UUIDs and Cryptographic Hashes Cause Severe Disk Fragmentation:
Sequential keys (AUTO_INCREMENT) append cleanly to the rightmost leaf with a 15/16 page fill factor (~93.75% density).
Random 40-char Git SHA-1 or 64-char Bitcoin hashes land randomly across leaf pages. When a 16KB page is full, InnoDB executes a 50-50 Page Split, dropping storage density to ~50% and causing severe buffer pool churn.
The Solution: Use an auto-increment integer clustered PK and store the hash in a secondary index packed as BINARY(32).

2.3 Covering Indexes (Eliminating Clustered Bookmark Lookups)

A query that must perform secondary-to-clustered bookmark lookups across millions of rows takes seconds. By adding all requested columns into the composite index, MySQL satisfies the query directly from RAM in milliseconds: 

-- SLOW: Scans secondary index then executes 1,000,000 clustered bookmark lookups (1,850ms)
SELECT pickup_location_id, pickup_datetime, total_amount
FROM nyc_yellow_taxi_trips
WHERE pickup_location_id = 132;

-- OPTIMIZATION: Composite Covering Index
CREATE INDEX idx_covering ON nyc_yellow_taxi_trips (pickup_location_id, pickup_datetime, total_amount);

-- FAST: All columns satisfied entirely from index leaf nodes (12ms - 150x speedup!)
-- EXPLAIN Output: 'Using index' in Extra column

Module 3: Concurrency, MVCC & Transaction Tuning (Weeks 9 - 12)

Learn how MySQL achieves high throughput using Multi-Version Concurrency Control (MVCC) and how to design financial ledgers with 100% mathematical deadlock immunity.

3.1 MVCC & Undo Log Version Chains

Under REPEATABLE READ and READ COMMITTED, readers never block writers and writers never block readers. Every physical clustered row contains three hidden system columns:

  • DB_TRX_ID (6 Bytes): Identifies the transaction that inserted or last modified this row.
  • DB_ROLL_PTR (7 Bytes): Roll pointer pointing backward along the Undo Log version chain.
  • DB_ROW_ID (6 Bytes): Auto-generated surrogate row ID if no primary key is specified.

3.2 Mathematical Deadlock Immunity Pattern

Deadlocks occur when two concurrent worker threads acquire row locks in reverse sequence. We eliminate deadlocks mathematically using Canonical Lock Ordering via LEAST() and GREATEST(): 

-- Canonical Lock Ordering Transfer Stored Procedure Pattern:
SET @acct_first  = LEAST(p_from_acct, p_to_acct);
SET @acct_second = GREATEST(p_from_acct, p_to_acct);

-- Always lock in ascending numeric order regardless of transfer direction:
SELECT balance FROM accounts WHERE account_id = @acct_first FOR UPDATE;
SELECT balance FROM accounts WHERE account_id = @acct_second FOR UPDATE;

-- Execute atomic transfer
UPDATE accounts SET balance = balance - p_amount WHERE account_id = p_from_acct;
UPDATE accounts SET balance = balance + p_amount WHERE account_id = p_to_acct;
COMMIT; -- Verified 100% Deadlock-Free under 50+ concurrent threads

Module 4: Big Data Scaling, Partitioning & Petabytes (Weeks 13 - 16)

Manage hundreds of millions to billions of records across tablespaces using RANGE partitioning, partition pruning, and sub-10ms data lifecycle aging.

4.1 The Golden Rule of Table Partitioning

⚠️ Strict Primary Key Constraint:
Every unique and primary key on a partitioned table must include every column used in the partitioning function. If your table partitions by pickup_datetime, a primary key on id alone will fail with Error 1503. 
CREATE TABLE nyc_yellow_taxi_trips (
    trip_id BIGINT NOT NULL AUTO_INCREMENT,
    pickup_datetime DATETIME NOT NULL,
    total_amount DECIMAL(10, 2),
    PRIMARY KEY (trip_id, pickup_datetime) -- REQUIRED: includes pickup_datetime!
) ENGINE=InnoDB
PARTITION BY RANGE (TO_DAYS(pickup_datetime)) (
    PARTITION p2023_q1 VALUES LESS THAN (TO_DAYS('2023-04-01')),
    PARTITION p2023_q2 VALUES LESS THAN (TO_DAYS('2023-07-01')),
    PARTITION p2023_q3 VALUES LESS THAN (TO_DAYS('2023-10-01')),
    PARTITION p2023_q4 VALUES LESS THAN (TO_DAYS('2024-01-01')),
    PARTITION p_future  VALUES LESS THAN MAXVALUE
);

4.2 Zero-Downtime Data Purging (`DROP PARTITION`)

Standard DELETE FROM table WHERE date < '2020-01-01' scans millions of rows, acquires row locks, generates gigabytes of undo logs, and takes hours. 

-- INSTANT ZERO-DOWNTIME DATA PURGING (< 15 milliseconds):
ALTER TABLE nyc_yellow_taxi_trips DROP PARTITION p2020_q1;
-- Drops physical .ibd file instantly with zero undo/redo log bloat!
